# 🧠 Cognitive AI Companion: Long-Term Memory Architecture

This project implements a production-grade memory architecture for AI companions, specifically designed to solve the critical industry failures of **persona drift** and **temporal inconsistency**. 

Developed as a "Founding Engineer" technical solution for **OnceMore**, this system moves beyond simple context-window history. It implements a dual-layer memory system—**Episodic and Long-Term**—to manage the "state" of a user's life over long durations.

---

## 🏗️ System Overview
The architecture is designed as a **Cognitive State Machine**. It treats the LLM as a reasoning engine while using Python logic and MySQL persistence to enforce deterministic rules.

### 1. Episodic Memory (The "Experience" Layer)
Episodic memory captures the semantic "vibe" of past conversations to answer questions like *"What did we talk about yesterday?"*
*   **Embedding Model:** Utilizes `nomic-embed-text` via Ollama to convert interactions into high-dimensional vectors.
*   **Interaction-Pair Logic:** Instead of embedding just the user query, the system embeds the **User Message + AI Response** pair. This bakes the AI's confirmation into the vector, ensuring significantly higher retrieval relevance.
*   **Retrieval:** Uses **Cosine Similarity** to find the top 5 most relevant past interactions from the current session.

### 2. Long-Term Memory (The "Biography" Engine)
Long-term memory (LTM) stores structured, persistent facts about the user's identity, career, and preferences.
*   **Relational Versioning:** Facts are stored in MySQL with a `status` (`active`, `superseded`, or `retired`). 
*   **Conflict Resolution:** When a user switch is detected (e.g., switching from Google to Tesla), the system marks the old record as `superseded` (historical) and the new one as `active` (current).
*   **Chronological Injection:** The AI receives the user's entire history labeled as `[CURRENT]` or `[PAST/HISTORICAL]`, allowing it to answer "Where did I work before?" with 100% accuracy.

### 3. Multi-Fact List Extraction
Using the **Groq openai/gpt-oss-120b** model, the system utilizes a **List-Based Extraction Pipeline**. It can identify and save multiple distinct facts in a single turn (e.g., age, university, and degree) without the "single-track mind" issues found in smaller models.

---

## 🗃️ Database Design
The system uses a strict relational schema to ensure data integrity:
*   **`sessions`**: Tracks application-level conversation containers.
*   **`conversations`**: Stores the raw text of every turn.
*   **`conversation_embeddings`**: Stores the JSON-serialized vectors generated by the embedding model.
*   **`long_term_memories`**: The core engine. Tracks `memory_category`, `memory_key`, `memory_value`, and the versioning `status`.

---

## 🔀 LangGraph Workflow
The conversation flow is orchestrated via a directed workflow:

1.  **Retrieve:** Fetch the user's full SQL Biography (LTM) and perform a vector search for Episodic snippets.
2.  **Generate:** Produce a response strictly grounded in the retrieved biography to prevent hallucination.
3.  **Save Interaction:** Commit the current interaction to the conversational history.
4.  **Extract:** Utilize Groq 120B to identify a **list** of potential new facts from the message.
5.  **Compare:** A conflict-resolution node compares new observations against existing `active` LTM facts.
6.  **Route & Persist:** Determine if facts are `NEW`, `SAME`, or an `UPDATE`. Updates trigger an atomic "Supersede" operation in MySQL.

---

## 🚀 Key Engineering Innovations
*   **Strict Grounding Protocol:** The generation prompt forbids the AI from imagining details. If info isn't in the Biography, the bot is instructed to ask the user.
*   **Deterministic Reliability Guards:** Python-level validation gates ensure that if the LLM returns a Null value, the system logs the event and skips the save rather than crashing the database.
*   **Context-Aware Keys:** The Extractor is shown existing memory keys to ensure "Workplace" doesn't accidentally get saved as "Job" or "Company" in separate turns.

🔐 Design Philosophy
Reasoning vs. Enforcement: LLMs are probabilistic; databases are deterministic. This project uses the LLM to understand the meaning of a change, but uses structured Python logic and SQL constraints to enforce that change. This ensures the AI remains a reliable companion that truly "grows" with the user.
